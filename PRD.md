## 1. Overview

A self-hosted, offline web tool that turns a requirement / user story into
professional QA artifacts: a **requirement breakdown**, **acceptance criteria**,
**test cases**, a **coverage matrix + summary**, **edge cases**, **structured
test data**, **ambiguity flags (with severity)**, and **traceability/health
scores** — generated by a **local LLM** (no paid API, no data leaves the
machine). Inspired by `ai-testcase-generator-beige.vercel.app` but built on our
own stack and upgraded to a real QA/QC-grade tool.

The system is **two Go services** (`qa-core` + `qa-ai`) running on one Mac Mini,
with **Ollama native on the host** for Metal GPU access. Because the hardware
serves one generation at a time, requests are handled through a **strict FIFO
queue** (in `qa-core`) whose live status is visible to every user.

---

## 2. Goals & Non-Goals

### Goals
- Generate high-quality, **structured** QA artifacts from a requirement.
- Run **fully offline** on local hardware — zero per-call cost, no API key.
- Give QA/QC users a **professional, rich input form and output** (not a toy demo).
- Make the **one-at-a-time queue transparent**: everyone sees the service is
  busy and waits their turn, with live updates and no page refresh.
- Answer the questions a **QA lead** actually asks: *Did we cover positive/
  negative/boundary/security? How risky? How complete is this requirement?*
- Keep the stack **simple**: no Redis, no React, no heavy build pipeline.

### Non-Goals (v1)
- No accounts / user management (single shared access code only).
- No billing / pricing tiers; no XLSX (CSV + Markdown + Jira CSV only).
- No multi-machine scale-out (designed as a seam, not built).
- No Indonesian output (English-only — see §7).
- No persistent job history across process restarts (in-memory queue).
- No live Jira/TestRail **API** integration (export files only, import-ready).

---

## 3. Target Users & Hardware

- **Users:** QA engineers, manual testers, QA/QC leads (internal, trusted network).
- **Concurrency:** unbounded users, but **served strictly one-by-one** — even
  100 users simply queue and finish in order.
- **Deploy target:** Mac Mini, Apple Silicon **M2/M4, 16 GB** unified memory.
- **Dev machine:** MacBook Pro M2 Pro, 16-core GPU, 16 GB (stronger, but the
  model must fit the *deploy* box, not the dev box).

## 4. Tech Stack (locked)

| Layer | Choice | Why |
|---|---|---|
| **Backend** | **Two Go services** (`qa-core` + `qa-ai`), stdlib `net/http` | Clean separation (mirrors Leksa); AI is independently deployable/swappable |
| **`qa-core`** | Web UI, queue, SSE, exports, access code | The gatekeeper; owns concurrency |
| **`qa-ai`** | Stateless; builds prompt, calls Ollama, validates JSON | Called by core over HTTP, one request at a time |
| **Queue** | **In-memory buffered channel + 1 worker goroutine** (in `qa-core`) | Strict FIFO, one-at-a-time, **no Redis needed** |
| **Live status** | **Server-Sent Events (SSE)** | One-way server→browser push; updates queue with no refresh |
| **Frontend** | **HTML templates + Tailwind**, styled to look like **shadcn**; **htmx** for dynamic bits | No React, no build-heavy framework |
| **LLM serving** | **Ollama, native on host** (Metal-accelerated) | Cannot be Dockerized on macOS (no Metal in Linux VM); `qa-ai` reaches it via `host.docker.internal:11434` |
| **Model** | **Qwen2.5 7B Instruct** | Strong structured/JSON output + instruction-following; fits 16 GB (~5 GB quantized) |
| **Persistence** | None in v1 (optional embedded SQLite/BoltDB later — **never Redis**) | Single-process queue lives in memory |

**Why Go / no Redis:** Redis exists to share a queue across processes/machines.
We have one process on one box, so the queue is an in-memory channel. Goroutines
+ channels do natively what Redis would otherwise be bolted on for.

## 5. Functional Requirements

### 5.1 Input Form (full QA/QC-grade — all in v1)

**Core**
- **Requirement / user story** — multiline text (limit ~3,000 chars).
- **Application type** — Web · Mobile (iOS/Android) · API · Desktop · E-commerce · CMS · SaaS · Embedded.
- **Detail level** — Condensed · Standard · Detailed.

**QA/QC options**
- **Test type** — Functional · Regression · Negative · Boundary · Smoke · Sanity · Integration · E2E · Performance · Security · Usability · Accessibility · UAT.
- **Test design technique** — Equivalence Partitioning · Boundary Value Analysis · Decision Table · State Transition · Pairwise.
- **Output format** — Step-by-step · Gherkin/BDD (Given-When-Then) · Checklist.
- **Priority/Severity scheme** — P0–P3 / Critical–Low.
- **Risk model** — risk = Business Impact × Failure Probability (drives `risk_level`).
- **Include preconditions** — toggle.
- **Include test data suggestions** — toggle.
- **Generate edge cases** — toggle (default on).
- **Platform / device / browser matrix** — optional free text.

Each field becomes a variable injected into the LLM prompt. When **Application
type = API**, the generator additionally produces API test artifacts (§5.2.G).

### 5.2 Generation Features

**A. Requirement Breakdown (new — runs first)**
Decompose the requirement into features and sub-requirements *before* generating
ACs. e.g. "User can reset password" → email validation, token generation, token
expiry, password policy, session invalidation. Each gets a `risk_level`.

**B. Acceptance Criteria** — testable, reviewer-friendly criteria, tagged with
`severity` and `risk_level`.

**C. Test Cases** — per chosen format/technique, with preconditions, steps,
expected result, `covers` (AC traceability), and `risk`.

**D. Coverage Matrix + Coverage Summary** — maps requirement points → test cases
(traceability) **and** a summary count: positive / negative / boundary /
security, so a QA lead sees coverage shape at a glance.

**E. Edge Case Generator** — dedicated section (empty field, max length, Unicode,
concurrent requests, expired token, etc.).

**F. Structured Test Data Generator** — not just suggestions; structured sets:
`valid_emails`, `invalid_emails`, `boundary_values`, etc.

**G. API Testing Support** (when app type = API) — request examples, response
validation rules, and status-code tests.

**H. Ambiguity Detection (with severity)** — flags unclear/contradictory parts,
each rated **Critical / High / Medium / Low** (button color ≠ undefined auth flow).

**I. Requirement Quality Checker** — a **Requirement Health score (0–100)** with
checks: ambiguous terms, missing actors, missing validation rules, missing error
paths. Usable standalone before generating cases.

**J. Traceability Score (0–100)** — how complete the requirement coverage is,
derived from requirement coverage, ambiguity count, and missing ACs, plus an
explicit **`missing_areas`** list (e.g. "Error handling", "Session timeout").

### 5.3 Output / Export
- On-screen **results panel**: breakdown, ACs, test cases, coverage matrix +
  summary, edge cases, test data, ambiguities, health/traceability scores.
- **Export: QA Repository CSV** (FROZEN) — test-case-centric, supports manual
  execution, coverage review, and future TestRail/Zephyr import without schema
  changes. Columns:
  `TC ID, Title, Requirement ID, Requirement Summary, Acceptance Criteria ID, Test Type, Test Design Technique, Priority, Severity, Risk, Preconditions, Test Data, Steps, Expected Result, Coverage Type, Traceability Links, Status, Notes`.
- **Export: Jira CSV** (FROZEN, **kept separate** — Jira is issue-centric, not
  test-case-centric; one CSV cannot serve both well). Columns:
  `Issue Type, Summary, Description, Priority, Labels, Components, Acceptance Criteria, Risk, Test Type`.
- **Export: Markdown** — docs-friendly full report.
- **Example requirements** picker to demo the tool.

### 5.4 Queue & Live Status (core differentiator)
- All submissions enter a **single FIFO queue**; exactly one job runs at a time.
- **Global, live status visible to everyone:**
  - Idle → "✅ Available — submit now."
  - Busy → "⏳ Generating now · N in queue."
  - On submit into busy queue → "You're #K in line · est. ~T."
- Counts update **live via SSE** (no manual refresh): users watch `#3 → #2 → #1 → your turn`.
- Each generation expected to take **~30–90s**.
- **ETA = rolling average of the last 20 completed jobs** (not a fixed guess), so
  the estimate stays honest as model/load conditions change.

### 5.5 Access Control
- **Single shared access code** gate (like the reference's beta code). No accounts.

### 5.6 Language
- **English-only output** in v1. Reason: 7B models are most consistent in English
  for structured/technical output; Indonesian risks term drift and broken JSON.

## 6. Architecture

```
Browser (HTML + Tailwind/shadcn-style + htmx)
   │  POST /generate  (form fields + access code)
   │  GET  /events    (SSE: live queue status)
   ▼
┌─────────────────────────── qa-core (Go) ───────────────────────────┐
│  ├─ Access-code middleware                                          │
│  ├─ Queue: buffered channel  ──►  single worker goroutine           │
│  │                                   │  one job at a time           │
│  ├─ ETA tracker (rolling avg of last 20 jobs)                       │
│  └─ SSE broadcaster ◄── job state (queued / running / done)         │
└───────────────────────────────────┬─────────────────────────────────┘
                                     │ HTTP (one request at a time)
                                     ▼
┌─────────────────────────── qa-ai (Go, stateless) ──────────────────┐
│  ├─ builds prompt from form fields                                  │
│  ├─ calls Ollama, parses + validates JSON                           │
│  └─ JSON validator (max 3 retries, then graceful error)             │
└───────────────────────────────────┬─────────────────────────────────┘
                                     │ HTTP  (host.docker.internal:11434)
                                     ▼
                       Ollama (NATIVE on host) ──► Qwen2.5 7B (Metal)

Results rendered to panel; CSV / Markdown / Jira-CSV export client-side
```

- **One worker goroutine in `qa-core`** guarantees strict one-at-a-time execution;
  `qa-ai` therefore never receives concurrent requests (matches single Ollama instance).
- **SSE broadcaster** fans out queue-state changes to all connected browsers.
- **Scale-out seam:** the queue + worker is an interface; a future version can
  swap the in-memory worker for a multi-node dispatcher without touching the UI,
  and `qa-ai` is independently deployable.

## 6b. Development & Deployment Environment

Mirrors the EduAI-Tech (Leksa) conventions: **Nix flake for tooling, nothing
installed globally; Docker for deployment.**

### Repo layout (monorepo)
```
QA-Tes-Case/
  flake.nix · flake.lock        # dev shell: go, gopls, gofumpt, golangci-lint, air, make, jq, httpie
  PRD.md
  services/
    qa-core/   cmd/ internal/ Makefile Dockerfile .env(gitignored)
    qa-ai/     cmd/ internal/ Makefile Dockerfile .env(gitignored)
  compose.yml                   # deploy: qa-core + qa-ai (Ollama stays native)
```

### Local development
- **Nix flake** provides the Go toolchain + tooling. Enter with `nix develop`.
- **Ollama runs natively** on the host (`ollama serve`, `ollama pull qwen2.5:7b`) —
  **not** in Docker, so it gets Metal GPU acceleration.
- Run each service: `nix develop --command bash -c 'cd services/qa-core && set -a; source .env; set +a; air'` (hot reload via `air`).
- **No Docker needed for dev** — no Postgres/Redis (in-memory queue by design).
- Per-service **Makefile** with consistent targets: `help / dev / build / test / lint / tidy / clean`. Build: `CGO_ENABLED=0 go build -ldflags="-s -w"`.

### Deployment (Mac Mini)
- **Docker** packages `qa-core` + `qa-ai` via a root `compose.yml`.
- **Ollama remains native on the host** (Metal); containers reach it through
  `host.docker.internal:11434`.
- The macOS Docker runtime is **Colima** (same as Leksa).

## 6c. Scoring Policy (FROZEN — v1 default)

Both scores are **explainable**: every deduction is itemized so QA managers can
see *why*. Scores start at 100 and subtract penalties; the model proposes
deductions, server clamps to 0–100.

### Requirement Health Score — *requirement quality, before generation*

**Ambiguity penalties** (per flagged ambiguity):

| Severity | Penalty | Example |
|---|---|---|
| Critical | −20 | Authentication behavior unspecified |
| High | −10 | Password complexity undefined |
| Medium | −5 | Validation message not specified |
| Low | −2 | Button color not specified |

**Missing requirement components:**

| Missing item | Penalty |
|---|---|
| Primary actor | −10 |
| Business rule | −10 |
| Success path | −10 |
| Error handling | −15 |
| Validation rules | −15 |
| Acceptance criteria implied but unstated | −10 |

**Interpretation:** 90–100 Excellent · 75–89 Good · 60–74 Needs Clarification ·
40–59 High Risk · <40 Not Test Ready.

### Traceability Score — *coverage completeness, after generation (stricter)*

`Traceability = Coverage Completeness − Coverage Gaps − Critical Ambiguity Impact`

**Coverage completeness** (start 100): each requirement point not covered by ≥1
test case = **−15**.

**Coverage-type gaps:**

| Gap | Penalty |
|---|---|
| No negative testing | −10 |
| No boundary testing (when applicable) | −10 |
| No error-path testing | −15 |
| No security testing (for auth/payment features) | −15 |

**Ambiguity impact** (unresolved ambiguity lowers coverage confidence):
Critical −15 · High −8 · Medium −4 · Low −1.

**Interpretation:** 95–100 Fully Covered · 85–94 Minor Gaps · 70–84 Coverage Risk ·
50–69 Significant Gaps · <50 Unsafe To Release.

> Rationale these are platform-independent (web/API/mobile/SaaS), simple enough
> for a 7B model to apply, and explainable to QA managers.

## 7. LLM Output Contract

The model is prompted to return **structured JSON** (validated server-side,
**max 3 corrective retries**, then a graceful error to the user) containing:

```json

  "requirement_analysis": [
    {
      "feature": "Password Reset",
      "sub_requirements": [
        "Email validation", "Token generation", "Token expiry",
        "Password policy", "Session invalidation"
      ],
      "risk_level": "High"
    }
  ],
  "acceptance_criteria": [
    { "id": "AC-1", "description": "...", "module": "...",
      "severity": "High", "risk_level": "High" }
  ],
  "test_cases": [
    {
      "id": "TC-1", "title": "...", "type": "Functional",
      "technique": "Boundary Value Analysis",
      "preconditions": ["..."], "steps": ["..."],
      "expected_result": "...", "covers": ["AC-1"],
      "format": "step-by-step | gherkin | checklist",
      "risk": "Critical"
    }
  ],
  "edge_cases": [
    { "id": "EC-1", "scenario": "Expired token", "expected_result": "..." }
  ],
  "test_data": {
    "valid_emails": ["..."],
    "invalid_emails": ["..."],
    "boundary_values": ["..."]
  },
  "api_tests": [
    { "request_example": "POST /reset { ... }",
      "expected_status": 200, "response_validation": "..." }
  ],
  "coverage_matrix": [
    { "requirement_point": "...", "covered_by": ["TC-1", "TC-2"],
      "coverage_type": "Positive" }
  ],
  "coverage_summary": { "positive": 12, "negative": 8, "boundary": 4, "security": 3 },
  "ambiguities": [
    { "location": "...", "issue": "...", "suggestion": "...", "severity": "Critical" }
  ],
  "requirement_health": {
    "score": 82,
    "rating": "Good",
    "deductions": [
      { "reason": "Validation rules unspecified", "points": -15 },
      { "reason": "High ambiguity: password policy undefined", "points": -10 }
```

- Export layers (CSV / Markdown / Jira-CSV) are pure transforms over this JSON.
- Scores (`requirement_health`, `traceability_score`) are model-proposed but
  sanity-bounded server-side (0–100).

## 8. Non-Functional Requirements
- **Reliability:** server never crashes under load — excess requests queue, not fail.
- **Bounded retries:** malformed JSON retried at most 3× then surfaced as a clear error.
- **Memory:** model + Go app + OS must stay within 16 GB (no swap thrash).
- **Transparency:** queue position/status and ETA always truthful and live.
- **Privacy:** all inference local; no requirement text leaves the machine.
- **Simplicity:** single Go binary + Ollama; minimal ops.

---

## 9. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| 7B output quality below API-grade | Strong structured prompt + JSON validation/retry; larger model if box upgraded |
| Malformed JSON from model | Validate + auto-retry, **hard cap 3 retries**, then graceful error |
| Misleading ETA | **Rolling average of last 20 jobs**, not a fixed estimate |
| Queue lost on restart | Accepted in v1; optional SQLite/BoltDB later |
| Long queue under heavy burst | Honest live ETA; scale-out seam ready |
| Memory pressure on 16 GB | Quantized model, single worker, monitor RSS |
| Scores feel arbitrary | Document derivation; bound 0–100; show `missing_areas` for justification |
